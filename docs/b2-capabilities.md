# B2 capability map for voice and speech AI

This page lists the Backblaze B2 capabilities that the architectures in this repository rely on. For each capability it states what it does, what it requires, its limitations, which architecture uses it and where the Backblaze documentation lives.

Architecture ids used in the table:

- `voice-training-data-lifecycle`: collecting, validating, versioning and releasing voice datasets.
- `batch-voice-generation-and-dubbing`: storing generation inputs, candidates, reviewed outputs and approved deliveries.
- `voice-agent-session-archive`: archiving finished voice agent sessions, evaluating them and selecting them for review or analytics.

Product documentation is authoritative for service behavior and limits, which can change. Prices and allowances are never copied here: the [B2 pricing page](https://www.backblaze.com/cloud-storage/pricing) is the source. Configuration templates for the capabilities marked as configurable live in [`examples/`](../examples/README.md).

| S3-compatible API | Lets existing S3 SDKs, CLIs and tools read and write B2 buckets by pointing them at the regional B2 endpoint. | An application key (key ID and key) and the endpoint of the account's region. | Covers the S3 operations these architectures use. The S3-Compatible API page lists the differences from AWS S3: ACLs are limited, IAM roles, object tagging and website configuration are not part of it, and naming rules differ slightly. Lifecycle, replication and Event Notifications rules are configured through the B2 native API, CLI or web console. | All three | [S3-Compatible API](https://www.backblaze.com/docs/cloud-storage-s3-compatible-api) |
| Presigned URLs and CORS | Presigned URLs give a browser or a partner time-limited GET or PUT access to one object without sharing a key; CORS rules let browser code on an allowed origin call the bucket. | A key with the capability the URL grants (for example `writeFiles` for uploads) held by the server that signs; a CORS rule on the bucket for browser use. | Browser uploads with presigned POST are not supported; use presigned PUT. A presigned URL is a bearer credential until it expires. | All three: contributor uploads, candidate review and session playback | [S3-Compatible API](https://www.backblaze.com/docs/cloud-storage-s3-compatible-api), [CORS rules](https://www.backblaze.com/docs/cloud-storage-cross-origin-resource-sharing-rules), [CORS with the S3-compatible API](https://www.backblaze.com/docs/cloud-storage-enable-cors-with-the-s3-compatible-api) |
| Multipart upload with retry, resume, complete and abort | Uploads a large object in independently retried parts, lists the parts already stored to resume after a failure, then completes or aborts the upload. | `writeFiles` on the target bucket; the client keeps the upload ID and part ETags; browser multipart needs `ETag` in the CORS exposed headers. | Parts other than the last are at least 5 MB and at most 5 GB; a large file is at most 10 TB. Uploaded parts are stored, and billed, until the upload is completed or cancelled; a lifecycle rule can cancel unfinished uploads. | All three: long recordings, dataset archives, generated stems | [Large files](https://www.backblaze.com/docs/cloud-storage-large-files), [S3 Create Multipart Upload](https://www.backblaze.com/apidocs/s3-create-multipart-upload), [S3 List Parts](https://www.backblaze.com/apidocs/s3-list-parts), [S3 Abort Multipart Upload](https://www.backblaze.com/apidocs/s3-abort-multipart-upload) |
| Application keys with limited scope | Gives each component its own key, limited to named capabilities, one or more buckets, one file name prefix and, optionally, an expiry. | A key with `writeKeys` to create others. The secret is shown only once, at creation. | A key admits a single name prefix, which is why the layouts use one bucket per zone. Keys created with an expiry last less than 1,000 days. The master key has no restrictions and is not used by applications. | All three | [Application keys](https://www.backblaze.com/docs/cloud-storage-application-keys), [S3-compatible app keys](https://www.backblaze.com/docs/cloud-storage-s3-compatible-app-keys) |
| Event Notifications with a signed, idempotent webhook | Sends an HTTPS POST to a webhook when objects matching a rule are created, deleted or hidden, signed with HMAC SHA-256 in the `X-Bz-Event-Notification-Signature` header. The receiver verifies the raw body and processes each `eventId` once. | Access enabled for the account through Backblaze Support; `writeBucketNotifications`; an HTTPS endpoint that answers 200 within three seconds and defers heavy work; a 32-character alphanumeric signing secret stored outside the repository. | Delivery is at least once, so duplicates must be expected. Up to 25 rules per bucket; prefixes of rules with the same event type cannot overlap; a rule uses one event category. Delivery attempts are metered as Class D transactions. The webhook cannot point to a Backblaze host. | `voice-training-data-lifecycle` (validate new clips), `batch-voice-generation-and-dubbing` (start review of candidates), `voice-agent-session-archive` (start session evaluation) | [Event Notifications](https://www.backblaze.com/docs/cloud-storage-event-notifications), [reference guide](https://www.backblaze.com/docs/cloud-storage-event-notifications-reference-guide), [b2_set_bucket_notification_rules](https://www.backblaze.com/apidocs/b2-set-bucket-notification-rules) |
| Versions and lifecycle rules | Every upload to an existing name creates a new version; lifecycle rules hide versions a number of days after upload, delete hidden versions after a number of days, and cancel unfinished large files. | `writeBuckets` to set rules. Rules are set as one list per bucket. | Setting rules replaces the bucket's whole list. Up to 100 rules per bucket; values are whole days of one or more; rules run once per day. Overlapping prefixes take the smallest value. An empty prefix applies to the whole bucket. A rule cannot delete a version protected by Object Lock. | All three: expiring incoming and work data, keeping release history | [File versions](https://www.backblaze.com/docs/cloud-storage-file-versions), [Lifecycle rules](https://www.backblaze.com/docs/cloud-storage-lifecycle-rules) |
| Server-side encryption | Encrypts object data at rest with AES-256, either with keys managed by Backblaze (SSE-B2, settable as the bucket default) or with a key the client sends on every request (SSE-C). | `writeBucketEncryption` to set the default. For SSE-C, the application stores and supplies the key. | Applies only to objects written after it is enabled. Metadata, file names and bucket names are not encrypted, so they must not carry personal data. Backblaze cannot recover a lost SSE-C key, and Cloud Replication does not copy SSE-C objects. | All three: SSE-B2 as the bucket default in every zone | [Server-side encryption](https://www.backblaze.com/docs/cloud-storage-server-side-encryption) |
| Object Lock | Makes object versions immutable for a retention period (governance mode, which keys with `bypassGovernance` can override, or compliance mode, which nobody can shorten) or until a legal hold is removed. | Object Lock enabled on the bucket (at creation, or once on an existing bucket); `writeBucketRetentions` for the bucket default; file retention and legal hold capabilities for per-object settings. | Cannot be disabled once enabled. Cannot be enabled on a bucket that is a replication source. Locked versions cannot be deleted by lifecycle rules or by anyone until retention ends, which also means storage for them continues. | `voice-training-data-lifecycle` (consent records and released datasets), `voice-agent-session-archive` (sessions under a retention or legal hold) | [Object Lock](https://www.backblaze.com/docs/cloud-storage-object-lock) |
| Cloud Replication | Copies new objects, and optionally existing ones, from a source bucket to a destination bucket in the same or another region or account. | A verified email and payment history; a source key with read access and a destination key with write access (not the master key); the destination bucket must exist; one account per region. | At most two replication rules per bucket. Deletes, hide markers, later metadata changes and SSE-C objects are not replicated; replicas cannot be replicated again. If the source uses Object Lock, the destination must too. The destination's lifecycle rules apply to replicas. | `voice-training-data-lifecycle` (released datasets), `voice-agent-session-archive` (protected sessions) | [Cloud Replication](https://www.backblaze.com/docs/cloud-storage-cloud-replication), [replication rule with the native API](https://www.backblaze.com/docs/cloud-storage-create-a-cloud-replication-rule-with-the-native-api) |

| Delivery through compute partners | Training, generation and transcription jobs on a partner GPU or compute provider read from B2 through the S3-compatible API, with egress to that partner not counted against the allowance. | An account with a partner listed on the pricing page; a read-only key scoped to the bucket and prefix the job needs. | Only providers on the partner list qualify; check the list before planning. Throughput depends on the provider's network and the job's parallelism. | `voice-training-data-lifecycle` (training reads), `batch-voice-generation-and-dubbing` (generation jobs) | [B2 pricing](https://www.backblaze.com/cloud-storage/pricing), [integration guides](https://www.backblaze.com/docs/cloud-storage-integration-guides) |
| Private delivery through a CDN | Serves objects from a private bucket through a CDN; for example, a Cloudflare Worker signs each request to B2 with an application key and the CDN caches the response. | A private bucket; a key held by the CDN worker, scoped to the published prefix; bucket info that allows caching; a CDN account. | Requests that carry an authorization header are not cached unless the bucket's cache settings allow it. Per-user authorization belongs to the CDN or the application, not to B2. | `batch-voice-generation-and-dubbing` (approved deliveries and published audio) | [Private content through Cloudflare CDN](https://www.backblaze.com/docs/cloud-storage-deliver-private-backblaze-b2-content-through-cloudflare-cdn), [Cloudflare integrations](https://www.backblaze.com/docs/cloud-storage-cloudflare-integrations) |
| Standard B2 | Pay-as-you-go object storage that holds every zone in these architectures: incoming, work, releases and protected records. | A B2 account and buckets in the chosen region. | Works alongside a low-latency session store, a message queue and a GPU-local cache, which keep those roles; see each architecture's boundaries. The region is chosen per account. | All three | [B2 documentation](https://www.backblaze.com/docs/cloud-storage), [data regions](https://www.backblaze.com/docs/cloud-storage-data-regions) |
| B2 Overdrive | A separate, high-throughput B2 offering with dedicated storage and network capacity, S3-compatible, for sustained high-throughput reads such as repeated full-dataset passes across a GPU cluster. | Enabled for the account by Backblaze on request, under a contract with a storage commitment and a minimum stored volume stated on the product page. | Fits when sustained aggregate read throughput, not storage size, is the constraint. Burst reads, archives and small datasets stay on standard B2. | `voice-training-data-lifecycle` only, when training reads are sustained and large | [B2 Overdrive](https://www.backblaze.com/cloud-storage/b2-overdrive) |
| Local processing or GPU cache | Jobs copy the shards or files they need from B2 to local NVMe or a cluster cache, work there, and write results back to B2. B2 remains the durable source; the cache is disposable. | Local disk sized for the working set; a read key for inputs and a separate write key for outputs; a manifest that records which version was read. | The cache is not durable and is not shared across sites. Cache invalidation follows the release version, not object timestamps. Random small reads straight from B2 during training are slower than reading from a local cache. | `voice-training-data-lifecycle` (training), `batch-voice-generation-and-dubbing` (model weights and inputs on the GPU host) | [B2 for AI and machine learning](https://www.backblaze.com/docs/cloud-storage-ai-machine-learning) |

## Selection criteria and trade-offs

- **Upload path.** Clients that only upload use presigned PUT URLs from a server that holds the key. Objects larger than a single comfortable request use multipart upload with resume, and a lifecycle rule in every zone cancels uploads that never finish.
- **Read path for training.** Start with standard B2 and a local cache on the GPU host. Run compute at a partner when egress to the job's location matters. Consider B2 Overdrive only when sustained aggregate read throughput is the measured bottleneck.
- **Delivery path.** Short-lived presigned GET URLs suit reviewers and a small number of recipients. A CDN in front of a private bucket suits repeated public or semi-public delivery of approved audio.
- **Protection.** Object Lock in governance mode for records that must not be deleted by mistake; compliance mode only where a regulation or contract demands it, because nobody can shorten it. Cloud Replication for a second copy in another region; it does not replace Object Lock, because deletes are not replicated but overwrites of unlocked objects are.
- **Automation.** Event Notifications start processing when objects arrive. Because delivery is at least once and a webhook must answer within three seconds, the receiver verifies the signature, records the `eventId`, answers, and hands the work to a queue or job runner outside B2.
- **Zones.** Each zone is its own bucket because lifecycle, Object Lock, replication, encryption defaults and notification rules are configured per bucket, and a key admits a single prefix. A sample may collapse zones into one bucket with prefixes when it says so.
